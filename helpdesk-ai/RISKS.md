| ID | Risque | P | I | Mitigation | Statut |
|---|---|---|---|---|---|
| R-01 | **Redondance du corpus** (≈58 types de tickets récurrents) → risque de fuite de données et de généralisation limitée | Élevé | Élevé | Séparation train/test sans fuite ; prétraitement plus fin ; enrichissement des données ; évaluation sur test dé-dupliqué | Ouvert |
| R-02 | **Sur-apprentissage** (CV F1=1.0 vs test 0.77) | Élevé | Moyen | Régularisation, augmentation, validation honnête, métriques par classe | Ouvert |
| R-03 | **Classe *Sécurité* à faible rappel** (36,4 % mesuré Phase 12 sur `best_pipeline.pkl`, cible ≥ 0.70 ; le chiffre ~20 % était une estimation antérieure aux corrections FORCE_RULES v1.1) | Élevé | Moyen | Augmentation de données, focal loss, fine-tuning CamemBERT, heuristiques | Ouvert |
| R-04 | **Hallucinations LLM** dans la synthèse RAG admin (`llama3.2:3b` local, Ollama) : vérifié en direct (2026-07-30) — avec un prompt few-shot ancrant le format, le modèle utilise fidèlement les vrais ID/score/catégorie fournis, mais reste un modèle 3B sur CPU : résumés parfois pauvres si la donnée source l'est déjà, pas de garde-fou empêchant une reformulation qui s'écarte légèrement du contenu fourni | Moyen | Moyen | Few-shot dans le prompt (`api/services/llm_service.py`), dégradation gracieuse vers un récapitulatif brut si Ollama indisponible/lent ; pas de vérification automatique de fidélité (Faithfulness RAGAS non branché sur ce flux) | Ouvert |
| R-05 | **Non-conformité RGPD** (données personnelles) | Moyen | Élevé | Anonymisation, registre de traitement, rétention (Phase 2) | Ouvert |
| R-06 | **Délai 6 mois** insuffisant pour tout le périmètre | Moyen | Élevé | MoSCoW strict, backlog, une tâche à la fois, jalons mensuels | Ouvert |

| R-14 | **Split de test non représentatif** : `data/splits/test.csv` (GroupShuffleSplit anti-fuite par Titre, 46 train/12 test Titres) ne contient **aucun exemple** des catégories *Backup* et *Communication* (0/356) — le F1-macro rapporté (ENF-03, 0.685) est calculé sur les classes réellement présentes, pas sur les 8 catégories du domaine ; risque de sur-interprétation déjà anticipé par PLAN.md Phase 12 (« sur-interprétation liée à la redondance du corpus ») | Élevé | Élevé | Découvert en construisant la matrice exigences→résultats (Phase 12, `CADRAGE_SRS.md` §5) ; nécessite un split stratifié (ex. `StratifiedGroupKFold`) ou plus de Titres uniques par catégorie rare avant de pouvoir mesurer un F1-macro fiable sur les 8 classes | Ouvert |
| R-15 | ~~**Feedback client trompeur**~~ : le bouton 👍/👎 + correction affichait « Merci pour votre retour ! » sans rien envoyer au serveur | Moyen | Élevé | Corrigé (2026-07-06) : `POST /tickets/{id}/feedback` implémenté et branché sur `ticket-detail.ts` (client), persistance vérifiée par relecture API indépendante après rechargement complet | **Clos** |
| R-16 | **Aucun routage différencié par confiance** (EF-05) : `create_ticket()` fixe `statut="En attente"` sans condition pour tout ticket, vérifié en pratique avec des confiances de 0.78 et 0.91 (même traitement qu'un ticket peu fiable) — le seuil et les indicateurs `auto_routed`/`low_confidence` sont calculés mais ne pilotent aucune automatisation de workflow | Faible | Moyen | Découvert en étude utilisateur légère (Phase 12, `CADRAGE_SRS.md` §6.4) ; décision de produit à prendre : assumer l'absence d'auto-routage (reformuler EF-05 au mémoire) ou l'implémenter | Ouvert |
| R-17 | ~~**Courses multi-processus non gérées lors de la migration PostgreSQL/ChromaDB**~~ : (a) `Base.metadata.create_all()` non tolérant à 2 workers uvicorn créant les tables simultanément sur une base Postgres neuve (`duplicate key ... users_id_seq`) ; (b) collection ChromaDB mise en cache par processus — un worker ne voyait pas les écritures faites par l'autre (RAG live retournant la suggestion générique au lieu de la solution admin réellement archivée) | Élevé | Élevé | Trouvés et corrigés en vérification live (2026-07-29), pas en test automatisé — `api/db/database.py::_create_tables()` et `api/db/vector_store.py::_get_collection()` ; reproduit et confirmé résolu par test manuel (curl) sur base vide | **Clos** |
| R-18 | **Couverture de test automatisée absente sur les fonctionnalités 2026-07-16→30** (boucle RAG live, refonte workflow tickets, migration PostgreSQL/ChromaDB, assistant de triage IA) — toute la vérification de cette période a été manuelle (curl + navigateur), aucun test ajouté à `tests/test_*.py` | Moyen | Moyen | À couvrir avant la soutenance si le temps le permet — au minimum un test d'intégration sur `approve_ticket()` (transitions + édition post-clôture) et un test sur `vector_store.query_similar()` | Ouvert |
| R-19 | **Latence de l'inférence LLM sur CPU** : synthèse IA (Ollama, `llama3.2:3b`) mesurée à 20-60s par requête selon la longueur du prompt (pas de GPU dans l'environnement Docker Desktop courant). Revu 2026-07-30 (retour utilisateur) : la synthèse est désormais déclenchée **automatiquement** à l'ouverture d'un ticket ayant un cas connu (remplace l'ancien bouton à la demande, jugé trop peu visible — la suggestion brute non reformulée restait affichée par défaut) — chaque ouverture d'un tel ticket coûte donc un appel LLM, latence potentiellement plus visible en usage courant et à la démo | Moyen | Faible | `OLLAMA_TIMEOUT=90s` avec repli automatique (`source:"fallback"`) ; état de chargement explicite côté UI (spinner + message d'attente) ; `Solution` appliquée déjà connue (score ≥ 0.50) requise pour se déclencher, pas les cas "nouveaux" sans candidat | Ouvert |
